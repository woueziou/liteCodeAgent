# GitHub Project sync

Board owner `woueziou`, linked repo `woueziou/liteCodeAgent`.

## New tickets go through the local buffer, not a direct `gh issue create`

`tracker` drafts a ticket locally with `litecode ticket new` — no GitHub call happens at draft time. The `sync` agent is the only one that turns that draft into a real issue, via `litecode ticket sync --apply`, batching every dirty ticket's creates/edits/comments into one bounded run instead of each agent making its own scattered `gh` calls. If you are `tracker`, do not skip ahead to `gh issue create` yourself; if you are anything other than `sync`, do not call `gh issue create`/`item-add`/`item-edit` on a brand-new ticket either — that is `sync`'s job.

Status/Priority/Size are pushed to the board **once**, at that first sync (the item doesn't exist on the board before then). After that, those three fields are **pull-only**: `litecode ticket sync` reads them back from the board into the file, never the other way around. Everything below this section — moving an existing item's Status, reading board state — still applies as-is; it is how `dispatcher`/`implementer`/`reviewer`/`triage` move an *already-created* item through the pipeline, which was never routed through the ticket buffer.

## Where the IDs come from — never hand-write them

Every project/field/option ID lives in **`.claude/data/board.json`**, generated by `litecode board init`. Read that file; never paste an ID into a prompt, a doc, or this skill. A hand-copied ID is how a board ends up with two different values for the same status.

```bash
BOARD=.claude/data/board.json
PROJECT_ID=$(jq -r '.projectId' "$BOARD")
STATUS_FIELD=$(jq -r '.fields.Status.id' "$BOARD")
IN_PROGRESS=$(jq -r '.statusRoles.inProgress.optionId' "$BOARD")
```

Statuses are addressed by **role**, not by label: `backlog`, `planned`, `inProgress`, `blocked`, `review`, `readyToMerge`, `done`. If `.claude/data/board.json` is missing or a role resolves to `null`, stop and report it — run `litecode board doctor` rather than falling back to a guessed ID.

## Status semantics: Review vs Ready to Merge

`review` = `implementer` opened a PR and got a `reviewer` verdict, but something still needs a human's judgment call before it can move forward (e.g. a `changes-requested` verdict that wasn't auto-fixed, or an edge case the reviewer flagged as worth a second look).

`readyToMerge` = the normal terminal state for a clean pipeline run: `reviewer` returned `approve` or `approve-with-notes` with no blocking findings, the PR is mergeable (no conflicts), and there is genuinely nothing left for a human to do except click merge.

## ⚠️ Never regenerate a single-select field's options wholesale

`updateProjectV2Field`'s `singleSelectOptions` input **replaces the entire option list**, and the input type carries no option `id` — so every option gets a **brand-new ID**, even if its name is unchanged. This silently invalidates every existing board item's stored value (they reference old option IDs that no longer exist), wiping the field on every item in one call.

This is why `litecode board init` refuses to add an option to an existing single-select field and reports it as a blocker instead. If a new Status option is genuinely needed: **add it in the project web UI**, which does it non-destructively, then re-run `litecode board init --apply` to refresh `.claude/data/board.json`, then `litecode board doctor` to confirm no item's status came back null.

## Labels vs Status (do not conflate)

GitHub labels (`bug`, `feature`, `doc`, `chore`) encode **what kind of change it is**. The board's `Status` field encodes **where it is in the pipeline**. Never use a label to represent pipeline state, and never put semantic type info in the Status field.

If the label a change needs doesn't exist yet, create it before creating the issue:

```bash
gh label create <name> --repo woueziou/liteCodeAgent --description "<one line>" --color "<hex>"
```

## Item-ID cache (avoid a full board fetch for status edits)

`gh project item-list` fetches the **entire board** in one GraphQL call — expensive, and the single biggest avoidable source of GitHub API quota usage when several agents run concurrently. A project item's node ID never changes once assigned, so it's safe to cache permanently.

Cache file: `.claude/data/github-project-item-ids.json` — a flat JSON map of `"<issue number>": "<item id>"`, committed to the repo so it's shared across all agent runs, not per-session.

**Before any `item-edit` on an existing issue's board item:**

1. Read `.claude/data/github-project-item-ids.json` and look up the issue number.
2. If present, use that item ID directly — do not call `item-list`.
3. If absent, fall back to `gh project item-list <n> --owner woueziou --format json --jq '.items[] | select(.content.number==<issue>) | .id'`, then **immediately write the resolved ID back into the cache** (merge, don't overwrite other entries).

**When creating a new issue**, write the newly-created item's ID into the cache directly — never rely on a later cache-miss lookup for an item you just created yourself.

Write it with `jq` so the file keeps a trailing newline (a missing one fails `bun run check` on projects whose formatter checks it):

```bash
CACHE=.claude/data/github-project-item-ids.json
tmp=$(mktemp)
jq --arg n "$ISSUE_NUM" --arg id "$ITEM_ID" '.[$n] = $id' "$CACHE" > "$tmp" && mv "$tmp" "$CACHE"
```

If a cache entry ever turns out stale (references a deleted item), delete just that key and let the next lookup re-resolve it — never wipe the whole file to fix one entry.

## Creating an issue and adding it to the board

This is what `litecode ticket sync` does internally for a brand-new ticket — reference only, not something to run by hand unless you are debugging `sync` itself. Draft with `litecode ticket new` and let `sync` push it.

```bash
BOARD=.claude/data/board.json
PROJECT_ID=$(jq -r '.projectId' "$BOARD")
NUMBER=$(jq -r '.number' "$BOARD")

ISSUE_URL=$(gh issue create --repo woueziou/liteCodeAgent \
  --title "<title>" --body "<body>" --label "<bug|feature|doc|chore>")

ITEM_ID=$(gh project item-add "$NUMBER" --owner woueziou --url "$ISSUE_URL" --format json --jq '.id')
# ... cache ITEM_ID per the snippet above ...

gh project item-edit --id "$ITEM_ID" --project-id "$PROJECT_ID" \
  --field-id "$(jq -r '.fields.Status.id' "$BOARD")" \
  --single-select-option-id "$(jq -r '.statusRoles.backlog.optionId' "$BOARD")"

gh project item-edit --id "$ITEM_ID" --project-id "$PROJECT_ID" \
  --field-id "$(jq -r '.fields.Priority.id' "$BOARD")" \
  --single-select-option-id "$(jq -r '.fields.Priority.options.Medium' "$BOARD")"

gh project item-edit --id "$ITEM_ID" --project-id "$PROJECT_ID" \
  --field-id "$(jq -r '.fields["Assigned Agent"].id' "$BOARD")" --text "human"

# Due Date — only when the request carries a real deadline
gh project item-edit --id "$ITEM_ID" --project-id "$PROJECT_ID" \
  --field-id "$(jq -r '.fields["Due Date"].id' "$BOARD")" --date "YYYY-MM-DD"
```

## Reading board state

```bash
gh project item-list "$(jq -r '.number' .claude/data/board.json)" \
  --owner woueziou --format json
```

Filter/parse with `--jq` rather than scraping issue comments — the board fields are the source of truth for pipeline state.

## Moving an item between statuses

Same `item-edit --field-id <Status field id> --single-select-option-id <role's optionId>` pattern, reading both from `.claude/data/board.json`.
